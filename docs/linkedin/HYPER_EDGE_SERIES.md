## The five educationals (verbatim drafts)

### 1. A claim needs its command
"Done" is not a deliverable. In my shop, `fixed`, `verified`, `landed`
are recollections until they name the command and the line it printed.
Not "all tests pass" but `golden_arrow --staged: 6 files, 0 new defects`.
Adopt this and half your status meetings evaporate. What's one claim you
made this week that couldn't name its command?

### 2. Verify by running, never by importing
Months of import sweeps missed a live NameError. An import answers "does
it load" — only a run answers "does it hold." I proved an ML library
native on Python 3.8 by executing it there, not by reading its imports.
The reading said stdlib-only. The run said it on 3.8. Trust the run.

### 3. A detector that trusts a shape instead of behavior will frame the innocent
My auditor flagged 12 "orphan" config knobs — dead settings nobody
reads. Except every one was read, through the canonical reader, in a
file the auditor never scanned. The tool was right about *a* thing and
wrong about *which*. Before you act on any finding, read the cited line.
Instruments need auditing too.

### 4. When the field won't clear, adapt the code to the value
Automating a form, one field resisted every select-all-delete while typed
text landed fine. Instead of fighting the widget, I created the thing it
wanted and declared it in the workflow. The on-screen value became
correct by construction. Stubbornness is a bug; routing around it is
engineering.

### 5. Ship the proof with the artifact
This week: a Python wheel published to PyPI with its sha256 matched
against the local build, install-tested clean, then announced. The
release note isn't "it's live" — it's the hash, the index response, and
the import line. Maximum exposure means nothing if the artifact can't
prove itself. `pip install eve-unleashed` — go check.
